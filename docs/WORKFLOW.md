# DayOS 개발 워크플로

## 1. 역할

| 누가 | 무엇을 |
|---|---|
| 오너 | 제품 기획, 기술적 의사결정(ChatGPT와 논의), PR 리뷰와 머지 |
| Claude Code | 구현, 테스트, 문서 갱신, PR 작성 |

## 2. 작업 흐름

1. **정한다.** 무엇을 만들지 합의한다. 결정이 안 된 것은 문서의 "열린 질문"에 적는다.
2. **브랜치를 만든다.** `main`에서 갈라져 나온 작업용 브랜치를 쓴다. `main`에 직접 올리지 않는다.
   - 이름 예: `feat/…`(기능), `docs/…`(문서), `fix/…`(버그)
3. **만들고 확인한다.** 코드를 쓰고, 테스트를 돌리고, 화면이 있으면 스크린샷으로 확인한다.
4. **PR을 연다.** PR(Pull Request)은 "이 브랜치 내용을 main에 합쳐 주세요"라는 요청이다. GitHub에서 변경 내용을 한눈에 보며 리뷰할 수 있다.
5. **오너가 리뷰하고 머지한다.** 머지는 GitHub에서 일어난다.
6. **로컬을 맞춘다.** 머지 후 로컬 폴더를 최신으로 만든다.

```bash
cd ~/dayos
git switch main
git pull
```

> GitHub는 코드를 **보관·리뷰**하는 곳이고, 실행은 코드가 있는 컴퓨터(로컬) 또는 배포된 서버에서 한다. 웹앱을 배포하면 URL로 열 수 있다.

## 3. PR에 꼭 적는 것

- 무엇을 바꿨는지 (변경 파일)
- 테스트 결과: 무엇을 실행해서 무엇이 통과했는지, **무엇은 확인하지 못했는지**
- 미확인 사항
- 예상 비용 (없으면 "없음")
- 화면 변경이 있으면 스크린샷
- 결정이 필요한 것

## 4. 커밋하면 안 되는 것

모델 가중치, 대용량 데이터셋, `.env`, API 키, 개인 일정 데이터. `.gitignore`가 대부분 막지만 커밋 전에 `git status`로 확인한다.

## 5. 다운로드가 필요한 작업

모델·데이터셋은 `docs/STORAGE_POLICY.md`의 순서대로 진행한다: 외장하드 확인 → dry run으로 크기·메모리 보고 → 오너 승인 → 다운로드 → 검증.

## 6. 문서 갱신

- 제품 요구가 바뀌면 `PRODUCT_SPEC.md`를 먼저 고치고, `ARCHITECTURE.md`와 `CLAUDE.md`의 영향받는 부분을 같이 고친다.
- 모델을 평가하거나 추가하면 `MODEL_REGISTRY.md`에 기록한다. 공식 Benchmark와 DayOS 자체 평가는 다른 표에 쓴다.
