# DayOS Architecture

> 상태: 초안 v0.1 (2026-11-01) · 설계 방향 문서이며 **아직 구현된 코드는 없다.**
> "제안"으로 표시한 것은 오너 승인 전이고, "미정"은 결정이 필요한 항목이다.
> 요구사항 출처: `docs/PRODUCT_SPEC.md`

## 1. 큰 그림

```
브라우저 (웹앱 UI)
   │
   ▼
앱 서버 ── 인증 / 사용자별 데이터 분리
   │
   ├─ 캘린더 서비스      일정 CRUD (사용자만 변경)
   ├─ 알림 서비스        규칙 기반, AI 미사용
   └─ AI 추천 서비스     사용자가 요청할 때만 동작
          │
          ├─ 동의 게이트 (Consent Gate)   외부 전송 전 검사
          ├─ 맥락 구성 (Context Bundle)   일정+선호+우선순위+피드백 요약 (읽기 전용)
          ├─ 제안 저장소 (Proposals)      AI 출력은 여기에만 저장
          ├─ 실행 기록 (Execution Log)    승인된 제안의 적용 결과
          └─ Model Layer
                ├─ ModelAdapter 인터페이스
                ├─ CloudApiAdapter   (MVP: API 모델 1개)
                ├─ LocalModelAdapter (나중: A.X 등)
                └─ ModelRouter       (나중: 작업·비용·개인정보에 따라 선택)
```

## 2. 가장 중요한 두 가지 구조

### 2.1 AI는 일정을 직접 바꿀 수 없다 (제안 → 승인 → 적용)

- AI 추천 서비스는 **캘린더 서비스의 쓰기 기능에 접근할 수 없다.** 읽기 전용 일정 조회와 "제안 저장"만 가능하다.
- 제안(Proposal)은 별도 데이터로 저장된다. 상태: `pending` → `accepted` / `rejected` / `expired`.
- 일정이 바뀌는 경로는 **사용자의 UI 조작** 또는 **사용자가 `accepted`로 바꾼 제안의 적용** 두 가지뿐이다. 적용 시 변경 내용을 사용자에게 다시 보여 준다.
- 승인된 제안을 적용하는 코드는 AI 경로 밖의 별도 실행 단계에서 사용자 세션 권한으로 동작하며, 제안 ID·승인 시각·변경 요약·결과(성공/실패/되돌림)를 **실행 기록**에 남긴다. 외부 서비스 호출이 생기면 같은 단계를 거친다 (MVP 없음).
- 개인화 데이터(선호, 우선순위, 피드백)는 AI 경로에서 읽기만 가능하다. 쓰기는 사용자 조작으로만 한다. 상세는 `PERSONALIZATION.md`.
- 이렇게 "권한 자체를 주지 않는" 구조로 원칙 2를 지킨다. 프롬프트로 "바꾸지 마"라고 부탁하는 방식에 의존하지 않는다.

### 2.2 외부 전송은 동의 게이트를 통과해야 한다

- 모델 호출 직전에 Consent Gate가 확인한다: 이 사용자가 **이 제공자**에게 일정 데이터를 보내는 데 동의했는가?
- 동의가 없으면 호출하지 않고 사용자에게 묻는다. 동의는 제공자별로 저장·철회할 수 있다.
- 전송하는 내용(어떤 일정 필드)을 사용자가 미리 볼 수 있어야 한다.
- 로컬 모델은 데이터가 기기/자체 서버 밖으로 나가지 않으므로 외부 전송 동의 대상이 아니다. (다만 로컬 모델을 어디서 실행하는지에 따라 달라질 수 있어 **미정**)

## 3. Model Layer (Model-Agnostic)

### 3.1 인터페이스 (개념, 제안)

모든 모델은 같은 모양으로 호출된다. 호출하는 쪽은 어떤 회사 모델인지 모른다.

```text
ModelAdapter
  describe()  -> ModelInfo        # 아래 3.2의 메타데이터
  generate(request) -> Response   # 텍스트/구조화 출력
  (옵션) tool calling, 스트리밍
```

- `CloudApiAdapter`: 외부 API 호출. 제공자별 구현(OpenAI, Anthropic, Google 등)은 필요할 때 추가한다.
- `LocalModelAdapter`: 로컬에서 도는 모델(llama.cpp, Ollama 등). 모델 파일은 외장하드(`docs/STORAGE_POLICY.md`).
- 두 Adapter는 **코드와 설정을 분리**한다. 한쪽을 추가·교체해도 다른 쪽과 호출하는 서비스는 바뀌지 않는다.
- **MVP는 CloudApiAdapter 하나, 모델 하나로 시작한다.** 나머지는 인터페이스가 막지 않게만 설계하고 구현하지 않는다.

### 3.2 모델 메타데이터

각 모델 설정에는 `docs/MODEL_REGISTRY.md` 기록 항목과 같은 정보를 둔다: 정확한 Model ID, 출시일, Revision, Total/Active Parameters, Context Window, License, 가격, 지연 시간, 하드웨어 요구사항, 데이터 처리 정책. 값을 모르면 `미확인`으로 둔다.

### 3.3 Model Router (나중)

작업 유형, 비용, 성능, 사용자 개인정보 설정에 따라 모델을 고른다. MVP에서는 만들지 않고, 호출 경로가 "모델을 이름으로 요청 → Router가 Adapter를 반환"하는 형태가 되도록 **자리만 열어 둔다.** (MVP에서는 설정에 적힌 하나를 그대로 반환)

### 3.4 평가

- 후보 모델은 **같은 평가셋**으로 비교한다.
- 제조사 공식 Benchmark와 DayOS 자체 평가는 **분리해서 기록**한다 (`MODEL_REGISTRY.md` §4, §5).
- 평가에는 정확도 외에 **승인 없이 일정 변경을 시도하는지**, 비용, 지연 시간을 포함한다.

## 4. 데이터와 개인정보

- **사용자별 데이터 분리:** 모든 데이터 행에 소유 사용자 식별자를 두고, 조회는 항상 그 사용자로 제한한다. (구현 방식은 DB 선택 후 결정, **미정**)
- **인증:** 방식 미정 (`PRODUCT_SPEC.md` 열린 질문 #1).
- **삭제:** 사용자가 요청하면 계정, 일정, 제안, AI 요청 기록, 동의 기록을 삭제한다.
- **AI 요청 로그:** 일정 원문 대신 최소 정보(요청 시각, 모델 ID, 토큰 수, 지연 시간, 제안 결과)를 남긴다.
- **비밀 값:** API 키 등은 환경변수/비밀 저장소에만 두고 저장소에 커밋하지 않는다 (`.gitignore`, `.env.example`).

## 5. 저장소와 외장하드

- 소스·설정·문서·평가 스크립트·모델 메타데이터는 Git으로 관리한다.
- 모델 가중치, 대용량 데이터셋, 캐시, Checkpoint는 외장하드 (`docs/STORAGE_POLICY.md`).
- 앱 서버가 클라우드에서 돌 경우 로컬 모델(외장하드)과 직접 연결되지 않는다. 로컬 모델은 당분간 **개발·평가용**이고, 제품 경로의 로컬 모델 제공 방식은 **미정**이다.

## 6. 기술 스택

**미정.** 웹앱이라는 것만 정해졌다. 선택 기준은 다음과 같다.

- 무료 인프라로 시작 가능할 것
- 인증, DB, 알림을 직접 만들 부담이 작을 것
- 사용자별 데이터 분리를 구조적으로 강제할 수 있을 것
- 개발자가 이해하며 유지할 수 있을 것 (`CLAUDE.md`)

후보와 비교는 별도 PR에서 조사한 뒤 오너가 결정한다. 그 전에는 앱 코드를 만들지 않는다.
